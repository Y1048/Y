# 손목 회전·미세 위치 조작 방식 검토

2026-09-17 / 기준 소스 `6c32983` / 로컬 시뮬레이션·기록 분석만 수행

## 판정

**“손 위치는 정확히 따라가고 불필요한 팔 움직임은 줄인다”는 요구는 맞다. 하지만 기존 구현도, 이번에 비교한 단순한 2단계 최적화도 최종 실행본으로 승인할 수 없다.**

팔을 고정하면 미세 위치 조작과 회전축 오프셋 보정이 불가능해지는 경우가 있다. 반대로 팔을 약한 비용으로만 억제하면 조건에 따라 억제가 사라진다. 매 순간 팔 속도를 최소화하는 것만으로는 긴 동작의 자연스러운 자세까지 보장하지 못한다.

이번 작업에서는 **실행 파일·런처·모델·IK 가중치·속도·PD·로봇 파일을 변경하지 않았다.** 새로운 코드는 실행 경로와 분리된 오프라인 검토 도구다. 사용자에게 다른 미검증 후보를 시험해 달라고 요청하는 대신, 실패를 재현하는 검증 자료를 먼저 고정한다.

Python 입력 매핑은 위치와 회전을 별도로 계산한다. 다만 CSV에 원본 Quest pose 전체가 없어 사람 손의 회전 중심, skeleton 방향, 위치 센서 흔들림을 이 자료만으로 교정할 수는 없다.

## 구현에서 확인한 원인

1. 사용자의 회전 의도가 아니라 **모델의 남은 위치오차**로 손목 우선 여부를 결정한다. 이전 동작의 지연만으로도 억제가 꺼진다.
2. 손목·팔꿈치·기본자세·어깨 편안함 목표가 같은 가중합에서 경쟁한다. 한쪽 비용을 바꾸면 다른 동작이 달라질 수 있다. 큰 damping 비용도 엄격한 작업 우선순위는 아니다. [Mink 공식 수식](https://kevinzakka.github.io/mink/background/derivations.html)
3. 몸통 앞 팔꿈치 보조는 높이 +8cm와 초기 좌우 위치를 향한다. 이동이 끝나도 앞쪽 영역에 남아 있으면 계속 활성화될 수 있다.
4. 기존 회전 검사는 중립 자세에서 30°씩 돌리는 조건이었다. 51개 회귀검사 통과를 비중립 자세·빠른 반전·미세 이동까지 자연스럽다는 증거로 해석한 것은 부적절했다.
5. **손 목표를 바꾸지 않고 유지해도 engage 자세를 향한 posture 목적이 팔을 움직인다.** 비중립 두 자세의 2초 사전 유지에서 팔 최대 변화가 4.74°/6.80°이고, 마지막에도 2.05°/s·2.97°/s로 움직였다. 따라서 뒤이은 1mm 조작에서 측정되는 팔 움직임을 전부 미세 이동에 필요한 양이라고 볼 수 없다. posture 목적을 제외한 비교 후보의 같은 유지 시험은 0이었다.

## 팔 보정이 실제로 필요한 경우

사용 중인 G1 모델에서 `right_wrist_pitch_link`와 추적 기준점 `right_wrist_yaw_link` 사이에는 **46mm** 간격이 있다. FK/Jacobian을 독립적으로 확인했다.

| 초기 자세에서 손목 축 | 추적 기준점의 위치 Jacobian 크기 |
|---|---:|
| roll | 0m/rad |
| pitch | 0.046m/rad |
| yaw | 0m/rad |

이 자세에서 pitch만 30° 돌리고 팔을 고정하면 기준점은 약 **23.8mm** 이동한다. 따라서 같은 기준점의 위치까지 고정하려면 팔 보정이 필요하다. 이는 해당 자세에서 특이점 때문이 아니다. 손목 회전 Jacobian의 특이값은 모두 1이었다. 다른 자세에서는 수치가 달라진다.

이를 숨기려고 제어 기준점을 바꾸거나 작은 사용자 위치 이동을 deadband로 지우지 않는다. 그런 변경은 정밀 조작의 의미를 바꾸는 별도 결정이다.

## 비교한 방식

| 방식 | 검토 결과 |
|---|---|
| 팔 고정 + 손목 3축 | 임의의 위치 3축과 방향 3축을 모두 만족할 수 없어 일반 해법으로 제외 |
| 현재 가중합 QP와 오차 기반 손목 비용 | 최신 기록 대부분에서 억제가 꺼지며 미세 조작·왕복 검사에도 실패 |
| 손목 6D 작업 → 동일한 선형 작업 출력을 유지하며 팔 속도 최소화 | 정밀도 비교 기준으로 유용하지만 빠른 반전과 긴 동작의 자세 누적 문제가 남아 채택 거부 |
| 작업 정확도 + 누적 자세·전환을 함께 검증하는 제한 최적화 | 다음 구현 방향. 구현·실험 결과로 증명하기 전에는 완성 해법으로 부르지 않음 |

2단계 prototype은 기존 충돌·관절범위·속도·가속도 제약을 재사용한다. 먼저 손목 pose 작업을 풀고, `Jv`를 보존하는 SVD 등식 아래 팔 4축의 속도를 줄인다. 팔을 고정하는 등식은 없다. [HQP 원 논문](https://gepettoweb.laas.fr/uploads/Publications/2014_escande_ijrr.pdf)

단, 이것은 선형화한 한 시점의 우선순위다. 다음 자세의 도달 가능성, 전체 경로, 자연스러운 팔꿈치 자세를 보장하지 않는다. 작은 LM 정규화와 손목 속도 비용도 남아 있어 완전한 다단계 사전식 최적화라고 부르지 않는다. QP 실패 시 1단계로 돌아가는 경로와 rank 변화도 연구 구현의 한계다. 이 prototype의 `elbow_assist_ticks`는 상속된 상태 표시이며 실제 elbow 비용 적용 횟수가 아니다.

## 고정한 검토 시나리오

생성한 31개 시나리오: 초기/뻗은 자세의 1·3·5mm 각 축 이동 18개, 비중립/접힌 자세/손목 한계 근처의 20° 회전 9개, FK 목표 왕복 2개, 20mm 이동과 회전 동시 입력 1개, 빠른 회전 반전 1개.

`reach_rotation_lag20mm`라는 이름의 시험은 **이미 쌓인 오차를 주입하는 시험이 아니라**, 20mm 위치 이동과 회전을 1초 동안 함께 입력하는 시험이다. 빠른 반전 사례가 방향 추종 지연을 따로 다룬다.

검토 기준은 결과를 보기 전에 정했다: 미세 이동 종료 오차 0.5mm/0.5°, 회전 종료 오차 2mm/1°, 왕복 관절 drift 3°. 이는 **제안한 소프트웨어 기준**이며 실제 센서 노이즈·G1 정확도 측정값이 아니다. 0.502mm처럼 경계에 걸린 실패도 임의로 기준을 넓혀 없애지 않는다.

팔 움직임 5° 기준은 별도 검토 지표다. 팔 고정 상태에서 같은 목표의 endpoint를 찾지 못한 경우, 움직임이 불필요하다고 단정하지 않고 판정 보류로 구분한다. endpoint 해가 있어도 속도·가속도·충돌을 만족하는 전체 경로가 있다는 증명은 아니다.

고정한 2초 사전 유지 과정에서도 컨트롤러별 자세가 달라질 수 있다. 생성 시험은 같은 시나리오 규칙 비교이며 완전히 같은 숫자의 목표 A/B는 아니다. 아래 CSV replay는 같은 기록 목표와 timestamp를 사용한다.

## 다음 구현의 채택 조건

1. 기존 제약을 유지하면서 손목 위치와 방향을 전체 7축으로 추종한다. 미세 위치 입력을 지우지 않는다.
2. 순간 팔 속도만이 아니라 같은 목표를 반복한 뒤의 자세 이탈·팔꿈치 벌어짐·왕복 drift를 제한한다. 팔꿈치 고정 높이로 해결됐다고 판단하지 않는다.
3. 작업 허용오차 안에서 자세를 고르는 방식이나 짧은 경로 예측을 검토하되, 허용오차는 결과를 본 뒤 늘리지 않는다. 엄격한 우선순위만으로 몸통 회피가 막히면 그 실패를 유지한다.
4. 현재 생성 시험의 실패/보류와 두 실제 기록의 악화를 모두 해소한 뒤 실행 경로 반영 여부를 판단한다. 회전 정밀도 하나만 좋아져서는 채택하지 않는다.
5. 다음 후보에서 ±방향 미세 이동, 장시간 반복, 몸통 앞 회전, 전환·복귀·재engage, 계산시간 꼬리분포까지 확인한다. 현재 31개로 이 모든 항목을 완료했다고 주장하지 않는다.

소프트웨어 문제를 사용자의 반복 VR 시험으로 찾는 횟수는 줄일 수 있다. 다만 **사람이 느끼는 자연스러움과 실제 센서·로봇 동작까지 오프라인으로 완전히 보장하거나 향후 피드백 0회를 약속할 수는 없다.** 먼저 여기서 드러난 실패를 자동 검사로 해결하고, 최종 사용자 확인을 분리한다.

## 재현

PowerShell, 저장소 루트에서 아래 명령을 사용한다. 엔진 경로는 실제 설치 경로에 맞춘다. 통신 프로그램을 실행하는 명령이 아니다.

```powershell
$env:PYTHONPATH = 'C:\Users\user\Desktop\G1_Teleop_Project\logs\diagnostics\mujoco_versions\3.12.0;' + (Get-Location).Path
py -3.11 -B experiments/twist2_right_arm_manual/audit_mink_precision.py --controller current --output logs/test_results/precision_current.json
py -3.11 -B experiments/twist2_right_arm_manual/audit_mink_precision.py --controller priority --output logs/test_results/precision_priority.json
```

프로그램 종료 코드 0은 보고서 생성 완료를 뜻한다. 채택 여부는 JSON의 `accepted`, `criterion_failures`, `proximal_criterion_inconclusive`를 함께 확인한다. 입력 CSV 원본은 수정·삭제하지 않았으며 재생과 생성 fixture는 실제 G1 측정으로 취급하지 않는다.
