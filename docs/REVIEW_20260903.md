# 전체 파일 조사 및 상세 코드 검토

기준: 2026-09-03 로컬 작업 트리. Git의 커밋 상태가 아니라 현재 파일을 대상으로 했다.

**전체 파일의 개별 정밀 검토는 아직 완료되지 않았다.** 전체 목록 조사와
지정 코드/설정의 정적 검사, 핵심 실행 경로 117개 파일의 본문 검토를 구분한다.
문제가 발견되지 않은 파일을 무결함으로 보증하지 않는다.

## 우선 수정할 사항

물리 시험을 확대하기 전에 R1~R3과 R15를 먼저 다루는 것이 적절하다.
현재 문제는 단순한 코드 길이나 Mink 라이브러리 선택보다, 최종 명령 검증과
종료 처리의 연결에 있다. 기존 제어기 전체를 교체하거나 제한값부터 완화할 이유는 없다.

### R1 · P1 · Gate 7 해제 실패가 성공으로 기록됨

- 위치: [gate7_live_arm_sdk.py](../hardware/g1_arm_bridge/gate7_live_arm_sdk.py), 746~809행.
- 본 루프 종료 후 `passed=True`를 설정한다. 이어서 `finally`에서 weight ramp와
  zero frame을 전송하지만 예외가 나면 `release_fault`만 기록한다.
- `passed`를 실패로 바꾸지 않고 `command_output_enabled=False`로 표시하며 종료 코드도 0이다.
- 첫 ramp 전송에서 실패하면 같은 `try` 안에 있는 zero-frame 구간도 건너뛴다.
  종료 시 설정 파일을 다시 읽으므로 파일 읽기 실패도 해제 전송을 막을 수 있다.
- 재현: 실제 finalizer AST만 추출하고 가짜 publisher에 `OSError`를 주입했다.
  결과는 **`passed=true`, `release_zero_frames=0`, `release_fault` 존재, exit code 0**이었다.
  SDK·네트워크·물리 출력은 사용하지 않았다.
- 영향: 정상 제어권 반환을 확인하지 못했는데도 시험 성공으로 해석할 수 있다.
  이 결과만으로 로봇의 실제 정지 여부를 판단할 수는 없다.
- 조치: 로드된 설정을 유지하고, 종료 결과를 별도 검증해야 한다. 해제 실패 시
  성공을 취소하고 비정상 종료로 기록한다. 마지막 명령 전송과 로봇의 제어권 반환 확인도 구분한다.
- 회귀 시험: ramp 첫 전송 실패, zero tail 중간 실패, 설정 파일 접근 실패,
  LowState 소실, 정상 종료를 각각 검사한다.

### R2 · P1 · Ruckig 적용 후 실제로 보낼 경로의 충돌 검사가 없음

- 위치: [ruckig_gate7_controller.py](../hardware/g1_arm_bridge/ruckig_gate7_controller.py),
  86~120행; [gate7_live_dry_run.py](../hardware/g1_arm_bridge/gate7_live_dry_run.py), 226~257행.
- 상위 Gate 7 결정 이후 Ruckig가 관절 목표를 다시 만든다. 이 결과에는 관절 범위와
  실측 대비 오차 검사가 있지만 최종 자세/이동 구간의 FK 충돌 검사가 없다.
- active 상태의 충돌 판단은 수신된 Mink 자세의 `minimum_clearance_m`에 의존한다.
  그 자세와 실제 G1의 비제어 관절 및 Ruckig의 중간 자세는 같다는 보장이 없다.
- Regular 복귀는 `MinimumJerkTrajectory`를 사전 검사하지만, 이후에도 Ruckig가
  경로를 바꾼다. [ruckig_joint_motion_limiter.py](../hardware/g1_arm_bridge/ruckig_joint_motion_limiter.py)
  71행의 `Synchronization.No`는 관절별 진행 비율이 같다는 보장도 하지 않는다.
- 재현: active 입력 10회를 처리하는 동안 등록된 collision path validator 호출은 **0회**였다.
  이 재현은 검사 누락을 확인한 것이며 실제 G1 충돌 궤적을 재현한 것은 아니다.
- 조치: 최신 전신 실측 자세를 기준으로 **최종 shaped command와 다음 이동 구간**을
  검사한 뒤 frame을 허용한다. 입력 목표에 붙은 충돌 플래그를 최종 명령의 증명으로 쓰지 않는다.
- 회귀 시험: 입력 목표는 충돌하지 않지만 관절별 보간 중 충돌하는 사례,
  허리/왼팔 자세 변화, 복귀 경로 재형성 사례를 포함한다.

### R3 · P1 · Gate 6 acquire 중 중단하면 weight가 올라감

- 위치: [gate6_arm_sdk_hold.py](../hardware/g1_arm_bridge/gate6_arm_sdk_hold.py), 631~645행.
- Ctrl+C 감지 시 release 시작점을 최대 weight로 강제한다.
- 실제 중단 분기 AST를 가짜 상태로 실행했을 때 **0.02 → 0.2**로 상승했다.
  운영자 의도는 해제인데 acquire 도중에는 제어권 비중이 순간적으로 증가한다.
- [test_gate6_interrupt_release.py](../hardware/g1_arm_bridge/test_gate6_interrupt_release.py)는
  이미 최대 weight인 시점부터만 검사하므로 이 결함을 발견하지 못한다.
- 조치: 중단 시 현재 weight를 캡처하고 그 값에서 감소시킨다.
- 회귀 시험: acquire 10/50/90%, HOLD, RELEASE 중 반복 중단 모두에서
  weight가 상승하지 않고 zero tail이 끝나는지 검사한다.

### R4 · P2 · 오래된 Mink 패킷도 새 입력처럼 취급할 수 있음

- 위치: [arm_sdk_teleop_contract.py](../hardware/g1_arm_bridge/arm_sdk_teleop_contract.py),
  469행, 729~746행; [gate7_mink_wsl_relay.py](../hardware/g1_arm_bridge/gate7_mink_wsl_relay.py), 62~97행.
- `timestamp`를 파싱하고 전달하지만 만료 판단에는 사용하지 않는다.
  새 패킷마다 `_input_age_s`를 송신 당시의 `input_packet_age_s`로 덮어쓴다.
- 따라서 형식과 sequence가 맞는 지연 패킷은 전송/큐 대기 시간을 빼고 평가된다.
  재현에서는 `timestamp=1.0`, 증가하는 sequence, age=0인 입력을
  **`TRACK_MINK_RIGHT`, valid=true**로 받아들였다.
- 조치: 생성 시각·전송 지연·수신 후 경과 시간을 포함하는 freshness 계약을 만든다.
  Windows/WSL의 시계 기준과 허용 오차를 먼저 정의해야 하며, 서로 다른 monotonic 시계를
  직접 빼면 안 된다. 새로운 세션의 승인과 이전 세션 폐기도 함께 검사한다.
- 회귀 시험: 오래된 증가 sequence, 지연된 이전 세션, 프로세스 정체 후 backlog,
  정상 패킷, 허용 범위의 시계 오차를 구분한다.

### R5 · P2 · 문자열 "false"가 하드웨어 허가로 해석됨

- 위치: [gate7_live_arm_sdk.py](../hardware/g1_arm_bridge/gate7_live_arm_sdk.py), 152행;
  [gate6_arm_sdk_hold.py](../hardware/g1_arm_bridge/gate6_arm_sdk_hold.py), 181행;
  [g1_right_arm_jog.py](../hardware/g1_arm_bridge/g1_right_arm_jog.py), 245행.
- `bool(payload["hardware_output_authorized"])`는 비어 있지 않은 문자열을 true로 만든다.
- 격리된 설정 사본에 JSON boolean `false` 대신 문자열 `"false"`를 넣으면
  Gate 7 loader가 **허가=true**를 반환하는 것을 확인했다.
- 다른 CLI 확인과 선행 조건은 여전히 필요하다. 현재 정상 JSON 설정이 자동으로
  풀렸다는 뜻은 아니다. 직접 Python 실행 경로의 설정 검증 결함이다.
- 조치: 반드시 JSON boolean만 허용하고 문자열·숫자·null은 오류로 처리한다.
- 회귀 시험: `false`, `true`, `"false"`, `"true"`, 0, 1, null, 누락 필드를 각각 검사한다.

### R6 · P2 · Unity 실측 표시에서 역순/중복 패킷을 거부하지 않음

- 위치: [G1RobotStateUdpReceiver.cs](../Unity_G1_VR/Assets/G1Teleop/G1RobotStateUdpReceiver.cs),
  320~354행, 429행.
- 출처와 전신 관절 형식은 검사한다. 그러나 `LatestSessionId`와 `LatestSequence`는
  저장만 하며 이전 값과 비교해 거부하지 않는다. 패킷 생성 시각 만료 검사도 없다.
- 조건에 맞는 오래된 패킷이 도착하면 표시 관절값을 덮고 `latest_packet_time`도 갱신한다.
- 영향: 실측 화면이 뒤로 튀거나 멈춘 값을 최신 상태로 표시할 수 있다.
  이번 검토에서 Unity/Quest 런타임에 패킷을 주입한 것은 아니다.
- 조치: 출처별 session/sequence guard와 freshness 검사 후에만 표시 상태를 갱신한다.
- 회귀 시험: 100 → 99 → 100 → 101 순서, 이전 세션 재전송, 중복 반복 중 timeout을 검사한다.

### R7 · P2 · Unity 필터와 해제 시간이 FPS에 따라 달라짐

- 위치: [G1ExistingTargetUdpSender.cs](../Unity_G1_VR/Assets/G1Teleop/G1ExistingTargetUdpSender.cs),
  107~109행, 150행, 209~212행, 243행, 393행.
- 전송 주기가 찼을 때 누적 시간을 0으로 버리고 한 번만 전송한다.
  이후 필터와 pinch/추적 손실/workspace 시간은 실제 경과 시간이 아닌 `send_interval`로 계산한다.
- 60Hz 송신 설정을 가정한 같은 계산식의 오프라인 재현에서 0.5초 pinch는
  60FPS에서 0.5초, 90FPS에서 약 0.667초, 72FPS에서 약 0.833초,
  30FPS에서 1.0초가 필요했다. 실제 Quest 프레임률을 측정한 값은 아니다.
- 조치: 실제 경과 시간으로 필터와 상태 시간을 계산하고 송신 스케줄의 잔여 시간을 유지한다.
  밀린 입력을 몰아서 여러 번 보내는 방식은 피한다.
- 회귀 시험: 30/60/72/90/120FPS 및 불규칙 프레임 간격에서도 동일한 시간 기준을 확인한다.

## 추가 정밀 검토: Startup Recovery와 실측 입력

두 번째 검토에서 19개 파일의 본문을 추가 확인했다. 다음 R8~R12는 새로 확인한
문제다. 모두 P2로 분류했다. 초기화/시각화/오프라인 검증의 정확성 문제이며,
아래 결과만으로 실제 로봇에서 충돌이나 잘못된 명령이 발생했다고 단정하지 않는다.
물리 출력 경로에는 별도의 직접 LowState 검사와 승인 조건이 남아 있다.

### R8 · P2 · 관측 종료 시 마지막 LowState의 만료를 놓침

- 위치: [check_startup_readiness.py](../hardware/g1_arm_bridge/check_startup_readiness.py),
  219~244행, 361~362행.
- `TimedPacket.age_s`는 수신 순간에 한 번 계산된다. 관측 창이 끝나거나
  충돌 계산이 끝난 시점에 최신 패킷의 현재 age를 다시 검사하지 않는다.
- 격리한 가짜 시계/소켓으로 첫 0.2초 동안 20개를 받은 뒤 통신이 멈춘 상황을 재현했다.
  마지막 패킷이 **약 0.9초 전** 데이터인데 저장된 age는 0초여서
  **`DIRECT_TELEOP_READY`, blockers 없음**으로 나왔다. 설정 timeout은 0.25초다.
- 영향: 끊긴 스트림을 기준으로 `recovery_bypass_allowed=true`인 결과를 만들 수 있다.
  이 파일은 직접 모터를 제어하지 않으며, 이후 실측 재검사가 이 판정을 막을 수 있다.
- 조치: 수신 monotonic 시각을 보관하고 관측 종료 및 결과 확정 시점에
  **최신** 패킷의 freshness와 관측 구간의 공백을 검사한다. 과거 관측 샘플
  전체를 현재 시각 기준으로 stale 처리하면 정상적인 1초 관측도 실패하므로 구분해야 한다.
- 회귀 시험: 초반 burst 후 단절, 마지막 순간 단절, 충돌 계산 지연, 연속 정상 스트림.

### R9 · P2 · 복구 검증의 몸통/왼팔/하체 자세가 실측과 다름

- 위치: [simulate_startup_recovery.py](../hardware/g1_arm_bridge/simulate_startup_recovery.py),
  596~610행; [diagnose_initial_pose_collision.py](../hardware/g1_arm_bridge/diagnose_initial_pose_collision.py), 25~35행.
- 복구 초기화는 저장된 오른팔 7개 값만 읽어 기본 configuration에 덮는다.
  swept-path 검사에서 쓰는 `_joint_pose`도 `qpos0`로 전체를 초기화한 후
  오른팔 후보와 고정 왼팔 준비자세를 적용한다.
- 기존 MuJoCo 모델을 메모리에서 로드한 재현 결과,
  허리 yaw/왼어깨 pitch/오른 hip pitch를 `0.3, 0.4, -0.2 rad`로 두어도
  검사 helper 호출 후 **`0, 0.174533, 0 rad`**로 바뀌었다.
- 따라서 오프라인 복구 PASS는 이 기본 몸통/왼팔/하체 가정에서의 결과이지,
  임의의 실제 전신 자세에 대한 검증이 아니다. 초기 precheck의 29관절 검사와도
  서로 다른 자세를 검사한다. 편집기의 정적 검사 역시 기본 전신 자세를 사용한다.
- 조치: 복구를 실제 자세에 적용하기 전, 불변 전신 실측 snapshot에 오른팔 후보만
  덮어 쓰는 방식으로 모델 조건을 통일하고 snapshot과 모델/설정 해시를 결과에 기록한다.
- 회귀 시험: 오른팔은 같고 허리/왼팔/다리만 다른 두 snapshot에서 충돌 검사가
  실제로 다른 전신 configuration을 사용하는지 검사한다. 이번에는 충돌 궤적 자체를 재현하지 않았다.

### R10 · P2 · 기존 접촉이 더 깊어져도 복구 경로 검사 통과

- 위치: [simulate_startup_recovery.py](../hardware/g1_arm_bridge/simulate_startup_recovery.py),
  132~179행, 522~579행.
- 탈출 전에는 접촉 body pair가 기존 집합의 부분집합인지만 검사한다.
  같은 pair의 거리가 감소하거나 음수 penetration이 되는 것을 거부하지 않는다.
- 실제 `_validate_profile`에 거리 응답만 주입해 **5mm → -2mm → 15mm**를
  검사했더니 **`passed=true`, `escaped_initial_contact=true`**였다.
  이는 검사 함수의 허용 조건 재현이며 실제 G1 형상으로 그 궤적을 만든 것은 아니다.
- 기존 staged planner의 `_evaluate_order` 역시 초기 pair/개수만 검사한다.
  반면 RRT `_edge_is_valid`에는 초기 최소거리 기준 검사가 있어 서로 기준이 다르다.
- 영향: QP 뒤에서 속도/가속도를 다시 제한하거나 경로를 바꿨을 때, QP 자체의
  충돌 제약만으로 최종 결과가 안전하다고 볼 수 없다. 최종 swept 검증도 이 틈을 놓친다.
- 조치: 접촉 허용과 침투 악화를 분리하고, 쌍별 거리/허용 수치오차를 기준으로
  최종 경로를 검사한다. 새 geom 접촉을 body pair 단위 묶음이 숨기는지도 시험한다.
- 회귀 시험: 기존 접촉의 거리 악화, 새 접촉, 탈출 후 재진입, 정상 분리.

### R11 · P2 · 같은 패킷 안의 오른팔 값과 전신 값이 모순돼도 허용

- 위치: [gate5_lowstate_safety_monitor.py](../hardware/g1_arm_bridge/gate5_lowstate_safety_monitor.py), 285~305행.

## 추가 정밀 검토: 캡처·리플레이·가상 시험

네 번째 검토에서 recorder/replay/quality/regression/fault matrix/virtual E2E,
실험용 limiter wrapper, 관련 테스트와 BAT를 합해 **16개 파일**의 본문을 추가로 읽었다.
재현은 로컬 fixture와 가짜 transport를 사용했다. 실제 socket 생성은 예외를 내도록
차단했으며 Unitree SDK, Unity, viewer, G1 접속은 사용하지 않았다.

### R15 · P1 · 기록 재생 입력을 실행 중인 live 제어 경로가 구별하지 못함

- 위치: [gate7_mink_replay.py](../hardware/g1_arm_bridge/gate7_mink_replay.py), 68~76행,
  90행, 118~123행; [gate7_mink_wsl_relay.py](../hardware/g1_arm_bridge/gate7_mink_wsl_relay.py), 62~100행.
- 리플레이 기본 목적지는 live relay와 같은 localhost UDP 5008이다. `NormalizePayload`는
  session/sequence/timestamp를 새로 만들고 `input_packet_age_s=0`으로 바꾼다.
  `state_source=mink_simulation`과 active 상태는 유지된다. replay 세션명은 검증단의 거부 조건이 아니다.
- 재현: timestamp=1, age=99초인 기록을 normalize한 뒤 실제 relay 함수에 넣었다.
  가짜 transport로 3개가 전달됐고 실제 hardware trajectory factory가 만든 제어기를
  SDK-neutral 세션에서 실행하자 **HOLD_CURRENT → TRACK_MINK_RIGHT → TRACK_MINK_RIGHT**,
  각 tick에 command frame이 생성됐다. 충돌 callback은 대체 함수였으며 실측도 고정 fixture였다.
- 즉 **이미 별도 승인으로 하드웨어 adapter가 실행 중인 경우** 리플레이가 live 후보 입력으로
  들어갈 수 있는 구분 누락이다. 잠금을 자동으로 해제했다거나 이번에 로봇을 움직였다는 뜻은 아니다.
  물리 경로의 시작 조건·실측 제한·최종 excursion 검사는 여전히 남아 있다.
- 조치: replay/live 출처와 승인된 실행 세션을 명시적으로 분리하고, relay가 출처 정보를
  보존하도록 한다. live adapter는 replay를 거부해야 한다. 별도 replay 포트만으로 끝내지 말고
  동시에 실행됐을 때도 입력 provenance를 검사한다. 과거 age를 0으로 바꾼 데이터는
  실시간 추적 유효성의 증거로 사용하지 않는다.
- 회귀 시험: 승인된 live 세션에 replay가 섞이는 경우, 종료된 세션 재등장,
  정상 simulator 후보, 명시적인 오프라인 replay를 구별한다. 가짜 publisher로 먼저 검사한다.

### R16 · P2 · 서로 다른 기록/메타데이터와 역순 payload를 캡처 로더가 수락

- 위치: [gate7_mink_replay.py](../hardware/g1_arm_bridge/gate7_mink_replay.py), 30~65행;
  [gate7_capture_quality.py](../hardware/g1_arm_bridge/gate7_capture_quality.py), 55~98행.
- 두 로더는 파일 index와 offset, 개별 payload 형식은 검사한다. 그러나 manifest와 각 record의
  `capture_id`, record metadata와 payload의 session/sequence/mode 일치, payload 순서 검사는 없다.
- 재현: manifest ID=file-A, record ID=file-B, metadata sequence=500/501,
  실제 payload sequence=10/9인 두 행을 **두 로더 모두 수락**했다. metadata는 idle이고
  payload는 active였다. 실제 recorder가 이런 파일을 생성했다는 증거는 없으며 손상/혼합 입력 재현이다.
- 특히 기본 replay는 sequence를 새로 붙여 원래 역순 기록을 정상 증가 순서처럼 만든다.
  분석·회귀 기준 파일이 어떤 세션을 재현하는지 보장하지 못한다.
- 조치: 중복 metadata를 제거하거나 payload와 교차 검증하고, capture ID 및 세션별 순서를
  검사한다. 정상 재시작을 허용하는 세션 전이 정책도 정의한다.
- 추가 해시 한계: `CaptureSha256`은 payload만 해시한다. 같은 기록 간격을 0.02초에서
  0.2초로 바꿔도 해시는 같았다. 필드명대로 payload hash이며 전체 파일/시간축의 증명이 아니다.
  regression의 trace hash는 별도로 달라질 수 있으므로 모든 회귀 비교를 우회한다는 뜻은 아니다.
- 회귀 시험: capture ID 불일치, metadata 충돌, 중복/역순 sequence, 정상 세션 전환,
  offset만 바뀐 파일의 전체 기록 해시를 확인한다.

### R17 · P2 · 유효하게 저장한 짧은 캡처를 분석하면 0으로 나누기 오류

- 위치: [gate7_capture_quality.py](../hardware/g1_arm_bridge/gate7_capture_quality.py), 248~257행.
- recorder는 1개 이상 수신하면 성공이고 로더도 단일 패킷과 같은 offset을 허용한다.
  그런데 `_raw_metrics`는 총 duration과 gap 개수를 확인하지 않고 나눈다.
- 재현: **패킷 1개**, **offset=0인 패킷 2개** 모두 `ZeroDivisionError`가 발생했다.
  기존 동일 시각 테스트는 0/0.02/0.02/0.04/0.06초라 전체 길이가 0인 경우를 놓친다.
- 영향: 짧게 기록했거나 곧바로 종료한 세션에서 결과 보고서 대신 traceback만 나온다.
- 조치: 통계 산출에 충분한 표본/시간이 있는지 검사하고, 부족한 항목은 unavailable로
  표시하거나 명확한 재기록 안내와 실패 결과 파일을 남긴다.
- 회귀 시험: 1개, 모든 offset 동일, 중간 offset만 동일, 정상 연속 기록을 구분한다.

### PASS가 증명하지 않는 것

- quality, fault matrix, experimental replay는 return collision callback을 항상 true로
  대체한다. `collision_limit` 시험은 패킷의 플래그를 주입하는 것이며 G1 mesh 충돌 시험이 아니다.
- 가상 measured 값은 승인된 command target으로 즉시 갱신된다. 모터 지연·하중·PD 응답을
  재현하지 않으며 ideal-following 조건에서의 상태 전이/명령 형성 시험이다.
- regression은 기본 `Gate7TeleopController`, limited viewer는 1.25/3/6 배율의
  실험용 Ruckig, virtual E2E는 hardware factory를 사용한다. 서로 다른 제어 경로의 결과이므로
  하나의 PASS를 나머지 전부의 검증으로 간주하지 않는다.
- regression CLI는 baseline 없이 TRACE_ONLY이거나 baseline을 처음 써도
  `regression matched`를 출력한다. BAT는 모드를 별도로 안내하지만, 첫 PASS는 기존 정상
  동작과의 비교가 아니다. baseline 수락과 이후 비교 결과를 구분해야 한다.
- MuJoCo replay의 `--validate-only`는 모델에 pose를 대입한다. 재생 경로 전체의 충돌,
  물리 동역학 또는 실측 추종을 검증한 결과가 아니다.
- 기존 quality 3개와 fault matrix 1개, **총 4개 통과**했다. 이번에는 socket 생성 차단 상태에서도
  통과했다. 프로세스형 capture/replay 및 virtual E2E 테스트는 본문만 검토했다.

- 코드/설정 264개 해시는 그대로이고 하드웨어 허가 10개도 모두 boolean false다.

## 공통 확인 및 한계

- `G1WristSourceCompatibility.Update`는 매 프레임 씬 전체 binder 검색과 설정 덮어쓰기를 한다.

  25행에서 거부하지만 **설치된 MuJoCo 3.11.0으로 직접 로드하면 성공**했다.
  기본 텔레옵은 `g1_29dof.xml`에서 모델을 생성한다. 현재 텔레옵 실행 실패로 분류하지 않았다.

- one-run BAT의 재잠금은 정상적인 배치 흐름에 의존한다. 프로세스 강제 종료까지
  보장하는 원자적인 1회 허가 소비 방식은 별도로 검토해야 한다.

  모터 응답, 중력하중, 접촉력, 넘어짐 또는 펌웨어의 제어권 반환을 검증한 것이 아니다.

## 남은 정밀 검토

`source_checks.csv`의 `static_only` 147개가 남은 작업의 명시적 목록이다.
추가로 이 색인 밖의 원본 자료와 Unity 직렬화 asset 검토가 있다.
다음 순서로 이어가는 것이 적절하다.

1. Unity asset/실행 검증: prefab 참조 그래프, 절대 위치·회전·29관절 FK, Play 이후 정책 일치.
   지정 Unity C# 본문 검토는 마쳤지만 컴파일/런타임 및 vendor 코드 전체 검증은 아니다.
2. 남은 벤치마크·테스트/런처: PASS 기준, 파일/프로세스 수명. 카메라/저장 LowState의
   본문 검토와 패킷 단위시험은 진행했고 Unity 재연결·지연 프레임 실행 검증은 남아 있다.
3. 나머지 BAT/config/문서 및 외부 원본: 실제 호출 여부, 버전·설치 재현성, 문서와 구현의 차이.
4. Startup Recovery: 위 결함의 회귀 시험 보강과 실제 전신 snapshot 기반 검증.
   기존 보류된 strategy-atlas 실험은 이번 검토에서 재개하지 않았다.

검토와 수정은 분리한다. 위 결함을 수정한 뒤에도 물리 출력은 별도 승인 전까지 열지 않는다.
